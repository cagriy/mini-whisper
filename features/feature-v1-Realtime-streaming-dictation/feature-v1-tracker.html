Detail

Summary

Mini Whisper currently transcribes only after the user releases the hotkey: the whole recording is POSTed to the batch transcription endpoint, optionally cleaned up, then pasted. This feature makes dictation live — as the user speaks, transcribed text streams into a text area under the recording animation in the overlay. The user chooses between two streaming engines in Settings: OpenAI's Realtime API (default) or Apple's on-device speech recognition. In both cases the compound streamed transcript is the final raw transcript — it feeds the cleanup model (if enabled) and is pasted, replacing the batch transcription call entirely when streaming is enabled.

Scope

In scope:

  • Settings: streaming toggle (on by default) and engine picker (Realtime API default / on-device).
  • Live text area under the recording animation in the overlay, active while recording when streaming is enabled.
  • Realtime API engine: audio streamed over WebSocket to OpenAI's realtime transcription mode; partial text displayed live; compound transcript → cleanup (if enabled) → paste.
  • On-device engine: Apple speech recognition partials displayed live; its compound transcript is likewise authoritative (fully offline, zero transcription cost); requires the macOS Speech Recognition permission.
  • Fallback to the existing batch pipeline when the realtime connection fails or drops mid-recording.
  • Realtime-session token usage counted into the daily usage totals.

Out of scope / deferred: type-at-cursor streaming, scratchpad confirm-before-paste, local dictation history, live translation mode, voice editing commands, stream-response-only cut.

Technical direction (constraints)

  • Engine one: OpenAI Realtime API transcription-only WebSocket mode (intent=transcription) with gpt-4o-mini-transcribe — verified available; partial text arrives as delta events; same API key as today.
  • Engine two: Apple on-device speech recognition via pyobjc, consistent with the app's programmatic-PyObjC approach; adds the Speech Recognition permission.
  • The recorder's existing live tap must feed the streaming engine incrementally while still accumulating audio locally for the batch fallback.
  • The overlay stays the single recording UI; the text area extends it (shape/size settled by the design mockup).
  • Cleanup is unchanged: one pass over the compound transcript after recording completes.
  • Streaming disabled restores current behaviour exactly, including duration/silence gates and stale-result discard.

Detail

Accepted mockup: Caption Bar (artifact). Full design: feature-design-v1-Realtime-streaming-dictation.md.

Summary

While the user speaks, the selected streaming engine transcribes incrementally and partial text renders in a caption bar under the recording dots. The compound streamed transcript feeds cleanup (when enabled) and is pasted, replacing the batch transcription call. Streaming is on by default with the free on-device engine; disabling the toggle restores today's behaviour exactly.

Architecture

  • streaming/base.py — StreamingEngine protocol (start/feed/finish) and TranscriptSink callbacks; engines and controller are each testable with fakes.
  • streaming/audio_convert.py — stateful chunked float32→PCM16 resampler.
  • streaming/websocket_engine.py — shared cloud skeleton (background thread, buffer-until-open, finish handshake) with OpenAI / ElevenLabs / Speechmatics subclasses; streaming/on_device.py — SFSpeechRecognizer with on-device recognition and permission gate; streaming/factory.py — engine selection with fallback reasons.
  • pricing.py — per-minute and per-token constants, pricing_overrides escape hatch, per-dictation cost.
  • CaptionBarWindow in overlay.py; new caption/caption_unavailable UI events through the existing 100ms poll loop.

Failure handling

Every streaming failure routes to the batch pipeline over the locally accumulated WAV; the bar shows "live transcript unavailable". Finish timeout (5s) discards partial streams rather than pasting truncated text. Cleanup failures keep today's error semantics, including for on-device offline dictations.

Data & usage

config.json gains streaming_enabled, streaming_engine, pricing_overrides, and a month-scoped usage map (migrated from daily_usage). Menu shows Today: tokens · minutes · $ and Month: $.

Testing

Introduces pytest suite: converter equivalence, per-provider fixture transcripts, factory matrix, pricing maths, config migration, controller fallback matrix with fake engines. UI verified manually per acceptance criteria.

Risks

  • Provider schema drift — isolated per subclass, fixture tests fail loudly, batch fallback covers the gap.
  • VAD segmentation fidelity vs batch — cleanup smooths seams; engines switchable.
  • Pricing constants rot — single file plus config overrides.

Detail

Full plan: feature-plan-v1-Realtime-streaming-dictation.md against design v1.

Overview

The feature lands in eleven stages following the design's rollout order (§9): data and pricing foundations first, then the four streaming engines behind the StreamingEngine protocol, then the controller pipeline swap with batch fallback, then the two UI surfaces, and finally py2app packaging. Every stage leaves the app fully working — nothing calls the streaming package until Stage 8, which lands the streamed path and its fallback atomically, and streaming_enabled: false reproduces today's pipeline throughout. Test runner: uv run pytest -q; executed baseline 49 passed, 1 skipped.

Stages

1 — Config data model and usage store

Streaming defaults, month-retained provider-attributed usage store with daily_usage migration, Keychain accessors. Touches config.py, controller.py, app.py, tests/test_config.py.

2 — Pricing module and usage-row formatting

Cost constants, dictation_cost with overrides, shared menu-row formatter. New pricing.py + tests/test_pricing.py.

3 — Streaming foundations

Protocol seam, CompoundTranscript assembler, stateful float32→PCM16 converter proven equal to the batch resampler. New streaming/base.py, streaming/audio_convert.py.

4 — On-device engine

SFSpeechRecognizer behind a fake-able thin wrapper; authorization matrix unit-tested. New streaming/on_device.py; adds pyobjc-framework-Speech.

5 — Websocket skeleton + OpenAI Realtime

Background-thread engine skeleton (buffer-until-open, 60s cap, finish timeout) and the OpenAI subclass, fixture-driven. New streaming/websocket_engine.py; adds websockets.

6 — ElevenLabs and Speechmatics engines

Remaining subclasses, one fixture transcript per provider.

7 — Engine factory and recorder buffer listener

make_engine selection matrix (toggle/keys/permission → engine or None with reason); Recorder.set_buffer_listener — non-blocking, exception-swallowed, accumulation untouched.

8 — Controller streamed pipeline and batch fallback

Engine lifecycle on press/release, caption UIEvents, compound transcript → cleanup → paste, every failure row from the design's edge table taking the batch branch, usage/cost recording. Pre-existing controller tests pass unmodified (R2 guard).

9 — Caption bar window and app event wiring

CaptionBarWindow in overlay.py per accepted mockup; poll-loop wiring. Platform-only/UI stage: build check + manual verification.

10 — Settings section and menu usage rows

Hybrid: usage-event payload change is TDD; "Live Streaming" AppKit section and two menu rows verified manually.

11 — Packaging

py2app plist + includes; local bundle build and the design's acceptance pass. Config-only / integration-verified.

Cross-cutting concerns

  • Security — keys Keychain-only, never echoed or logged; wss endpoints are module constants (no SSRF surface); transcripts stay on the existing paste path.
  • Performance — non-blocking tap hand-off; 60s pre-connect buffer cap; 5s finish timeout; caption redraw only on text change.
  • Observability — engine lifecycle at INFO with concrete fallback reasons; per-event DEBUG; cost rows as billing observability.
  • Compatibility — one-shot lossless usage migration; silent config upgrade via defaults; the streaming toggle is the rollback at every stage.

Verification

After Stage 11: acceptance pass on the built .app — live captions with all four engines, forced-network-loss fallback with correct batch paste, Speech-denial fallback with pointer, menu rows matching pricing rates, byte-for-byte legacy behaviour with streaming off.

Planning decisions taken

  • Corrected a design grounding error in place: the repo already has a pytest suite (49 tests); new tests extend it and its conventions.
  • format_usage_rows lives in pricing.py so controller and app share it without circular imports.
  • Dependencies added in the stage that first imports them; py2app registration deferred to Stage 11.
  • config.usage_totals() added for the app's startup menu read; legacy menu format kept until Stage 10.
  • Compound-transcript state lives in a tested CompoundTranscript class in streaming/base.py.
  • Cloud engines split across two stages and factory paired with the recorder listener — staging-order choices the plan owns.

Deviations from the design

None — plan matches design v1 exactly.
