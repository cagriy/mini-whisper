Detail

Summary

Users dictate the same names, acronyms and project terms into many apps and the recognizer gets some of them wrong every time. Today the only recourse is a hand-maintained vocabulary list that reaches the batch transcription instructions and the cleanup prompt but never the streaming recognizer, and that cannot express "when you hear X, write Y". This feature lets the user correct a misheard phrase once, from the menu's last dictation or from a History row, and remember the pair as a rule scoped to the destination app or to all apps. Rules apply deterministically to every future transcript in scope, and their correct spellings are fed to the configured recognizer as hints where supported. It is the follow-up the v1 storm deferred as "automatic or edit-driven vocabulary learning".

In scope

  • Correct last dictation… in the menu bar menu and Correct… on each History row.
  • Correction dialog: select the mistaken phrase, type the correct spelling, preview. Phrase edit only.
  • Remember this correction with scope This app (default when a bundle ID exists) or All apps; no bundle ID requires the explicit global choice.
  • Copy corrected text; never pasted or submitted on the user's behalf. Cancel saves nothing.
  • Persisted rules with Heard, Write, Sounds like (optional), Scope and Enabled, stored alongside vocabulary in the shared config.
  • Deterministic local replacement: literal whole phrases, case-insensitive, whitespace-tolerant, applied once to the final transcript before paste and history. Never applied to the live caption. Historical entries stay as delivered.
  • Settings → Vocabulary: existing term chips plus a corrections table with edit, disable, delete and in-place validation.
  • Rule impact preview against History before saving; unavailable when history is off.
  • Misheard-terms tally of corrections made, remembered or not, shown in Settings with a nudge to remember recurring one-offs. No per-rule firing counts.
  • Recognition hints: SFSpeechRecognizer contextual strings; OpenAI Realtime keywords; Speechmatics custom dictionary with an explicit, prefilled, editable Sounds like field; batch OpenAI prompt field; cleanup prompt pairs and terms as delimited data.
  • SpeechAnalyzer hints only if the installed SDK accepts them; otherwise labelled unavailable, local rule still applies.
  • Settings reports skipped or unsupported hints per engine. Caps enforced when the request is built, never by deleting stored terms.
  • Manual vocabulary unchanged. README and CHANGELOG describe per-engine support and scope semantics.

Out of scope / deferred

  • ElevenLabs keyterms and their 20% premium billing.
  • Creating a rule directly in Settings without a dictation.
  • Pasting corrected text back into the original app.
  • Profile-scoped rules; a Correct affordance on the overlay; per-rule firing counts; live-caption correction; export/import of rules.
  • Automatic sounds-like derived silently from the Heard phrase.
  • Background monitoring of edits in other apps; project-folder or website scopes; model training; voice editing.
  • Regex, wildcard, fuzzy or chaining rules; rewriting past History entries.

Technical direction (constraints, not design)

  • The shared config.json stays readable and writable by the Python app, which round-trips the whole file; unknown keys keep being preserved here.
  • Bundle ID com.ips.mini-whisper, macOS 14, Swift 6 strict concurrency, no third-party runtime dependencies.
  • Rules applied exactly once to the final transcript, after optional cleanup, before paste and history; identical on every path; inserted text never rescanned; live caption never mutated.
  • One immutable vocabulary-and-rules snapshot per recording, captured with the starting app; final corrections use the release app against that snapshot; edits during a recording affect the next one.
  • App rule beats global rule for the same phrase; longer match beats shorter; stored order breaks ties.
  • Hints carry correct spellings, never mistaken ones, except the explicit Speechmatics sounds-like. Neither phrase is ever a cleanup instruction or a regex.
  • Provider limits (SFSpeechRecognizer 100 phrases; Speechmatics 1000 entries of up to 6 words; OpenAI keyword character rules) enforced at serialization.
  • Secrets stay in the Keychain; requests or URLs carrying hint terms are never logged.
  • Persist before reporting success; on write failure keep the draft, show the error, keep prior rules in effect. Settings refresh through the existing config-change consumer.
  • Measurement uses a small user-provided audio set; live provider runs are opt-in with configured credentials.
  • Timing tested on the virtual clock; TDD with an observed failing test before each implementation step.

Summary

The user corrects a misheard phrase once, from the menu bar's last dictation or a History row, and remembers it as a rule scoped to the destination app or all apps. Rules apply deterministically to every future transcript in scope, once, after optional cleanup and before paste, on every engine and path. The rule's correct spelling, the heard phrase and any sounds-like variants are sent as recognition hints where the engine documents a mechanism, so the recognizer is steered toward a form the rule already knows. Settings → Vocabulary gains a corrections table, a tally of phrases the user keeps correcting and a per-engine report of what was sent.

Goals and non-goals

  • Deterministic whole-phrase replacement in scope on streamed, batch, cleanup-on, cleanup-off and key-free paths.
  • App-scoped rules never touch other apps; every rule editable, disable and delete effective from the next recording.
  • Hints reach SFSpeechRecognizer, SpeechAnalyzer, OpenAI Realtime, Speechmatics, the batch prompt and the cleanup prompt, proven by request-contract tests; the batch request uses the documented prompt field.
  • Before/after measurement on a user-provided audio set per hint-capable engine; the result decides SpeechAnalyzer's label.
  • Non-goals: ElevenLabs keyterms and premium billing, manual pair entry in Settings, paste-back, profile scope, overlay correction, firing counts, live-caption correction, export/import, custom language models, DictationTranscriber, automatic sounds-like without a field, regex/fuzzy/cascading rules, rewriting history, background monitoring, model training, voice editing.

Architecture

  • MWCorrections (new, depends on MWConfig): PhraseKey, CorrectionResolver, PhraseMatcher, CorrectionApplier, CorrectionValidator, CorrectionSnapshot, RecognitionHints + HintResolver, HintSerializer, HintReport, HintSupport, CorrectionTally, ImpactPreview, PromptSections. Pure values, no I/O.
  • MWConfig: CorrectionRule and CorrectionTallyEntry types; Config gains corrections and correctionTally, known keys, decode-with-defaults, validation (trim, drop empties, keep first duplicate per scope).
  • MWStreaming: RecognitionOptions.contextualStrings; SpeechAnalyzerAPI.makeSession(locale:contextualStrings:) with AnalysisContext set before analysis; engines and adapters take RecognitionHints; EngineProvider.make(config:secrets:hints:).
  • MWTranscription: Transcriber.transcribe(wav:prompt:); OpenAIClient sends prompt, never instructions.
  • MWProfiles: PromptComposer.transcribePrompt(base:terms:) and cleanupPrompt(base:hints:rules:).
  • MWPipeline: RecordingSession gains startTarget and snapshot; ProcessingInput gains snapshot; UIEvent.result carries DeliveredDictation (text, app name, bundle ID, engine, time); DictationController captures the frontmost app at press and resolves hints; ProcessingJob applies rules once after cleanup.
  • App: Correction window (CorrectionSource, CorrectionModel, CorrectionView, CorrectionWindowController), MenuModel row and action, StatusItemController callback, UIEventRouter, History Correct… action, Settings CorrectionsEditorModel/CorrectionsEditor, SettingsModel.refresh(from:), AppDelegate composition.

Data model

"corrections": [{"id": "…", "heard": "eefa", "write": "Aoife", "sounds_like": ["eefa", "eva"], "bundle_id": "com.tinyspeck.slackmacgap", "enabled": true}],
"correction_tally": [{"heard": "eefa", "count": 4, "last": "2026-09-05T16:07:00Z"}]

Stored order is the precedence order; tally capped at 200 (evict lowest count, then oldest); no migration.

Wire shapes (additions)

  • SFSpeechRecognizer: request.contextualStrings, first 100 hints.
  • SpeechAnalyzer: AnalysisContext.contextualStrings[.general] set via setContext before analyzeSequence; a failure is logged and analysis continues.
  • OpenAI Realtime: session.audio.input.transcription.keywords, present only when non-empty, < > CR LF removed.
  • Speechmatics: transcription_config.additional_vocab entries {content, sounds_like}, up to 1000, entries over 6 words skipped and reported.
  • Batch: multipart prompt = transcribe_prompt.txt + "Vocabulary (spell exactly as written): …".
  • Cleanup: "Preserve these terms exactly as written: …" plus "Known corrections — replace the exact phrase on the left with the spelling on the right:" with one quoted pair per variant.

Failure and edge cases

  • Save failure keeps the draft, shows the error, leaves prior rules in effect (ConfigStore.update throws before caching or yielding).
  • No bundle ID forces All apps; history off degrades only the impact line; app switch between press and release keeps press hints and uses release rules.
  • Overlaps: longest, then app scope, then stored order; no cascade; no match inside longer words; possessives match through the apostrophe boundary.
  • Caps and character filters skip and report, never delete stored terms; empty hints leave every request shape unchanged.

Security and performance

Phrases never logged; all payloads JSON- or multipart-encoded; regex tokens escaped; no hint in any URL. Rule application compiles one regex per variant per job and runs in well under a millisecond; the impact preview runs over in-memory history on a cancellable background task.

Testing

One test file per MWCorrections component; contract tests for every request shape with and without hints; controller tests for press-time capture, snapshot immutability and release-time resolution on VirtualClock; job tests for rule application on every path; App tests for MenuModel, CorrectionModel, CorrectionsEditorModel, HistoryListModel and SettingsModel.refresh; opt-in HintMeasurementTests gated on MW_INTEGRATION=1 and MW_HINT_AUDIO_DIR writing per-engine reports.

Risks

  • Ordinary-word collision — mitigated by whole-phrase matching, scope, impact preview, Enabled switch.
  • SpeechAnalyzer hints may have no effect — measurement decides the label; dead path removed if unavailable.
  • Batch prompt change makes transcribe_prompt.txt reach the model — release note.
  • Provider contract drift — exact-JSON contract tests and the Settings report.
  • Inconclusive measurement — per-engine statements, no blanket accuracy claim.

Rollout

Single release, no flag. Order: MWConfig coding → MWCorrections → prompts and prompt field → pipeline → streaming hints → App surfaces → measurement and label → README/CHANGELOG. Rollback: disable or delete rules, or remove the two keys.

Cross-cutting concerns

  • Security — the only new log lines are counts (hints: N sent, K skipped, corrections: N replacement(s) from M rule(s)), pinned by R26 assertions. Every phrase reaching a provider is encoded by JSONEncoder or as a multipart text part, never concatenated into JSON; OpenAI's four forbidden characters are stripped before encoding. Every regex token is escaped with NSRegularExpression.escapedPattern(for:), so a phrase can never become a pattern. The stage order opens no insecure window: hints only leave the machine from Stage 6, by which point Stage 3's filters and caps are in place and tested.
  • Performance — resolvers are O(rules); the applier compiles one regex per variant once per job, with an N3 guard test at 300 rules over a 1,200-character transcript. Press latency gains one synchronous frontmost() call, the same one release already makes. Payloads are bounded by the 100/100/1000 caps; config growth by the 200-entry tally cap.
  • Observability — two new count-only log lines, a Log.config error on a failed rule or tally write, a Log.ui error on a failed preview or Copy. The Settings Recognition hints group is the live report of what each engine receives; the committed measurement reports are the record of whether it helped.
  • Compatibility / migration — no migration: both keys default to empty, older builds carry them through Config.extra, and the Python app round-trips them as unknown dict keys. Four shared signatures widen (Transcriber.transcribe, EngineProvider.make, SpeechAnalyzerAPI.makeSession, UIEvent.result), each with every site listed in its stage. RecognitionOptions gains a defaulted parameter, so its two construction sites are untouched.

Planning decisions taken

  1. PhraseKey lives in MWConfig, not MWCorrections — Config.validated() implements R4 and R6, and MWConfig cannot import MWCorrections without inverting the module dependency the design fixes. Design §5.1 corrected in place.
  2. RecognitionHints carries an ordered rules array plus vocabulary instead of a pronunciations dictionary — R21 fixes the order of additional_vocab and distinguishes rule entries from vocabulary entries; a Swift dictionary has no order and cannot make that distinction. Design §5.1 corrected in place; no wire shape changes.
  3. ResolvedRule is defined as { rule, variants, isAppScoped } — §5.1 used the type in three signatures without defining it. Design corrected in place.
  4. PromptComposer stays a struct — §5.3's sketch wrote enum; the existing declaration is a struct and nothing needs it changed. Design corrected in place.
  5. Engine hints (Stage 6) land before the pipeline's press-time resolution (Stage 7) — the reverse order would leave EngineProvider.make carrying a parameter no engine reads for a whole stage.
  6. Stage 5 resolves rules from a release-time snapshot; Stage 7 swaps to the press-time snapshot — this delivers R23 and R24 a stage earlier without waiting on R12, and the swap changes no observable prompt text.
  7. The measurement's manifest decoding, hit counting and report rendering live in MWTestSupport — the shipping modules carry no test-only code and R37's logic is still host-tested.
  8. The report directory is derived from #filePath, overridable with MW_HINT_REPORT_DIR — §5.4 fixed the path but not how a test resolves the repository root.
  9. MWCorrections is registered in project.yml in Stage 2, alongside Package.swift, though the app first imports it in Stage 8 — one registration point rather than two.
  10. HistoryListModel.engineLabel is promoted to internal in Stage 9, the stage whose correction-window source line first needs it.
  11. Stage 6 covers all four engines in one stage — widening EngineProvider.make forces every engine construction site to change together; a split would leave the cloud branch dropping a hints parameter for a whole stage.
  12. No feature flag — design §9 fixed a single release, and rules and hints are inert until the user remembers a first correction.

Deviations from the design

None — the plan matches design v2 exactly. The four corrections listed above are factual grounding fixes and internal under-specifications resolved in the design file in place; none changes scope, requirements, approach or an external interface.

Human verification

The app was deliberately never launched: it reads real API keys from the Keychain, spends the user's own provider credits, writes their real config.json and pastes synthesized keystrokes into the frontmost app. These checks need a person:

  • Dictate, open Correct Last Dictation…, select a phrase, confirm it snaps to whole words and the preview updates, Save.
  • Dictate the same phrase to the same app and confirm it is corrected; to a different app and confirm it is not.
  • Open Correct… from a History row.
  • Set history retention to 0 and confirm the menu route still opens and the impact line reads “History is off — no preview of past dictations.”
  • Tab through the correction window and confirm keyboard navigation reaches every control.
  • With Settings → Vocabulary open, save a rule from the correction window and confirm the table updates without reopening Settings.
  • Confirm the Settings Vocabulary pane renders the corrections table, detail form, Often corrected rows and Recognition hints rows as designed.
