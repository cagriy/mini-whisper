Detail

Summary

Mini Whisper's UI is six separate fixed-size windows in stock system styling, reached one at a time from the menu-bar menu, and its meeting summaries are four fixed sections set in two small columns. v6 gives the app one resizable main window — a sidebar with Meetings, Dictations and Settings, with meetings opening as pages inside it — a design language of its own modelled on the attached reference screenshots, and topic-based summaries that read as a document.

In scope

  • Main window. Resizable, opened from the menu bar. Sidebar: Meetings (home), Dictations (today's History list with its actions), Settings (the nine existing sections as a second level).
  • Meeting pages. Mode chooser including Test Call setup, the live meeting with notes, script and score panes, and the finished meeting. One meeting on screen at a time; a sidebar recording indicator returns to the live one.
  • Status-bar menu. Stays; its rows open the main window at the matching destination.
  • Design language. Defined, documented, light and dark, applied to the main window, Correction, Onboarding and About.
  • Summary format. New topic-based default prompt; renderer for headings, nested bullets, bold and paragraphs; old summaries still display.
  • Summary actions. Regenerate and Copy on a finished meeting.
  • Global search. One search across meetings and dictations.

Out of scope / deferred

  • Restyling the dictation overlay.
  • Editing summary text in place.
  • Ask-anything chat over meetings; agents keep the MCP server and CLI.
  • Calendar “Coming up” and starting a meeting from an event.
  • Folders; sharing, spaces, teams, accounts and plans; People and Companies pages; recipes.
  • Opening a meeting in a second window.
  • A Dock-app or launcher-panel shape for the app.
  • Any release from main while v6 is in progress.

Technical direction

  • macOS 14, arm64, Swift 6 strict concurrency, bundle ID unchanged.
  • Native SwiftUI/AppKit only; Sparkle stays the one third-party runtime dependency and MiniWhisperCore stays dependency-free.
  • Stays a menu-bar app: Dock icon only while a window is open.
  • New non-UI logic lives in core modules or host-testable models, written test-first.
  • Must survive the move: paste from history into the previously frontmost app, recording continuing when the window closes, Esc restoring a hotkey capture, no delete while a meeting is open, ⌘C/⌘V in text fields.
  • Summary is model output: links stay inert; the renderer copes with any Markdown an edited prompt produces and with summaries already on disk.
  • summary_prompt.txt stays user-editable and is never silently overwritten once edited; a stored summary changes only through Regenerate.
  • The reference is a model for structure and feel, not a source: no reference branding, icons, names or copy.
  • UI choices are settled on HTML mockups in both appearances; the accepted language is recorded in DESIGN.md.
  • App state lives in config.json; anything the window remembers respects that rule.
  • No release from main until v6 is complete; an urgent fix ships from a branch off the last release tag.

Summary

v6 gives Mini Whisper one resizable main window with a sidebar and pages for meetings, dictations, search, settings and a meeting from chooser to summary. Every window except the dictation overlay follows one design language in light and dark. Summaries become topic-based documents with Regenerate and Copy.

Goals and non-goals

  • Goals: one window for the whole app; a meeting as a page that can be returned to while recording; one documented language with a Theme setting; topic summaries in a reading column; Regenerate and Copy; one search; usage visible in the window.
  • Non-goals: restyling the overlay; editing summaries; chat, calendar, folders, sharing; a second meeting window; changing the menu-bar app shape; any release from main before v6 is complete.

Meetings as pages

MeetingCoordinator loses its windows and gains two closures, present and dismiss. It holds the chooser-or-live session, a stored meeting opened from the list, and stopped sessions kept alive off screen while their summary is written. Leaving the meeting page drops a chooser, keeps a recording, and releases a finished meeting. A meeting with a session cannot be deleted.

Summary

The parser is line-based: fenced code, headings, rules, unordered and ordered items with an indent stack, continuation lines, paragraphs; anything else is paragraph text. Inline bold, italic, strikethrough and code come from Foundation's inline Markdown with links and images removed. A Meetings row shows the topic headings, or the first sentence for a four-section summary, or the first transcript words in italics.

Regenerate and Copy

Regenerate emits .rewriting, then .ready (saved, billed, the old cost kept in the meeting total) or .kept with the reason (nothing saved or billed). Copy writes Markdown as plain text, escaped HTML with a fixed tag set, and RTF.

Data

  • config.json: theme (system, light, dark) and main_window_frame.
  • meeting.json: billing.replacedSummaryCostUSD, absent reads as 0.
  • index.json: unchanged shape; the excerpt follows the new rule when a meeting is next saved.
  • summary_prompt.txt: replaced only when it equals the previously shipped default.

Failure handling

  • A failed, declined or keyless Regenerate keeps the old summary and states why.
  • A saved frame off every display falls back to the default size, centred.
  • An edited prompt that yields no headings still renders; the row falls back to the first sentence.
  • Hiding the window cancels a hotkey capture and never touches a recording.

Security

Summary text is model output: links and images are never active, pasteboard HTML is built from escaped text, and no summary, transcript, dictation or search text is logged.

Testing

Swift Testing suites per component: SummaryDocument, MeetingStore excerpt and cost, regenerate branches, prompt migration, config keys, usage totals, navigation, coordinator session table, window model states, search debounce and cache on VirtualClock, frame policy, rich text. Acceptance is a hand check of R1–R24 in both themes.

Risks

  • Regressions as four windows become pages: each carried-over behaviour is a requirement with a model test and a hand-check line.
  • The coordinator's session lifetime is new logic: one table, one test per row, existing tests ported.
  • Stock controls and custom dialogs in a custom language: components wrap the common ones; all nine Settings sections are checked in both themes.
  • Release freeze while v6 is in progress: urgent fixes ship from a branch off v0.6.2.

Rollout

Seven stages on main, each leaving the app working: core; tokens and components; main window with Meetings, Dictations and Settings; meeting pages and the coordinator; search; Theme and the small windows; documentation and changelog. No flag. Released as 0.7.0. Data written by v6 is read safely by 0.6.2.

Overview

Core rules land first in MiniWhisperCore, test-first; then the design tokens and the host-tested app models; then the main window replaces the list windows, Settings and finally the meeting window; then the Theme setting, the small windows and the documents. Baseline on 5456c80: core 935 tests in 17 runs, app 307 tests in 34 suites, all green; app build succeeds.

Stages

Phase A — Core

  • 2. Theme and main-window-frame config keys — round-trip, unknown theme kept, malformed frame read as absent. MWConfig.
  • 3. Topic-based summary prompt and its migration — §5.3 text; legacy file replaced, edited file untouched. PromptFiles, resource, AppDelegate.

Cross-cutting concerns

  • Security: link and image stripping and HTML/RTF escaping land and are tested before any view or Copy uses them; the window frame is validated (Stage 2) and clamped (Stage 7) before AppKit sees it (Stage 10).
  • Performance: one parse per summary event; lazy block rendering; search loads each meeting once per session off the main actor; frame written only at hide, close and quit.
  • Observability: the §5.18 log lines, with Stages 4 and 8 asserting that no summary, transcript, dictation or query text is logged.
  • Compatibility: additive keys only; 0.6.2 reads everything v6 writes; intermediate states are mixed but working, never released.
