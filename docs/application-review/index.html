Preserve what works

  • Hold and tap recording share one shortcut; the overlay does not take focus.
  • Clipboard restoration checks for intervening copies before overwriting.
  • Correction rules have scope, impact previews, enable/disable, and deterministic application.
  • Keychain storage, local history retention, and no telemetry provide a useful privacy foundation.
  • Native controls and system colors already support much of Settings and History.
  • Overlay previews reuse production animators; reduced-motion simulation already exists.

Evidence: clipboard restoration, correction flow, production preview, and the surface inventory below.

One native language, two surface types

Keep standard macOS windows for editing and a quiet, temporary overlay for recording. Share status meaning, typography roles, copy, and accessibility behavior across both. The overlay does not need to resemble a settings form.

Design direction (Recommended)

Retain native macOS styling and invest in consistency, legibility, and state feedback. A broad visual rebrand would leave the most consequential workflow gaps unresolved.

This is a proposed design policy, not a tested UI mockup. Findings DS-01 through DS-10 contain the source evidence and acceptance criteria.

Settings hierarchy

Group around tasks: Dictation (engine, language, microphone, shortcuts); Text (cleanup, prompts, app profiles, vocabulary); Privacy & history; Appearance & sound; Providers; Updates. Start with better labels and cross-links. Validate the grouping before moving every pane.

Apple’s Settings guidance cautions that too many settings can make controls harder to find. Its Color guidance describes dynamic system colors. These support the direction; the specific findings come from this repository.

Sequence by dependency and user impact

This is a recommended order, not a release commitment. Fixes and feature extensions are related; do not count both as separate estimates when they share the same implementation.

First
Protect trust

Recoverable text and explicit routing

  • Retain recognized text through cleanup and paste failure; provide Copy and retry actions (UX-01, FT-01).
  • Show the effective speech / cleanup / fallback path; implement a hard local-only policy (UX-03, FT-02).
  • Provide persistent, accessible failure/status feedback and confirm destructive retention changes (UX-04, UX-06, UX-13, DS-01).

Exit: simulated cleanup, target disappearance, missing permission, and network failure preserve useful text without violating history-off or local-only settings.

Then
Make it learnable

First success, readable history, coherent editing

  • Replace repeated key setup with a path based on the chosen engine and a first-dictation rehearsal (UX-02, FT-03).
  • Expose shortcut behavior, stop/cancel, full transcript detail, and action results (UX-05, UX-07, UX-08).
  • Align save feedback, control semantics, readable type, resizable windows, and copy (UX-09, DS-02–DS-10).

Exit: a new user completes one dictation without an OpenAI key on a supported local engine, reads a long result, and corrects a phrase using keyboard navigation.

Afterward
Expand deliberately

Language, input control, and result reuse

  • Add microphone and language preferences, task presets, and a visible effective profile (FT-04–FT-06).
  • Add prompt previews, selected correction-pack import/export, and local cost/reliability detail (FT-06–FT-08).
  • Add optional review before insertion on top of pending results; explore Shortcuts text return after policy and delivery are dependable (FT-09, FT-10).

Exit: test each feature against its finding’s completion criterion; validate demand before the larger automation workflow.

Defer

More decorative overlay styles, team workspaces, sync, meeting bots, and subscription infrastructure. The repository already has six overlay styles; a stronger daily dictation loop has a clearer connection to this app’s purpose.

Scope, evidence, and limits

Reviewed the Swift app at version 0.5.0, commit a83561b. Three subagents independently examined UX, new feature opportunities, and design language. The consolidating review cross-checked the highest-impact code paths and removed overlapping recommendations.

What this review establishes

Findings describe source-observed behavior or clearly labeled opportunities. No native app session, live dictation, paid provider request, VoiceOver audit, or user study was performed. No personal history, configuration, or stored credentials were inspected. Visual clipping and accessibility consequences that require runtime testing remain hypotheses, not reproduced defects.

Historical mockups and feature plans are context only; current production source determines whether a feature exists. This report changes no application code.

How to read the evidence

Each finding links to immutable source lines on GitHub. “Source-confirmed” means the stated code behavior is visible; it does not establish frequency or user impact. “Runtime validation needed” identifies a plausible interaction or rendering risk. Feature effort is an informed relative judgment from the architecture.

Native validation still required

  • Fresh install and denied/revoked permissions; supported local-engine setup without credentials; model download failure.
  • Hold vs tap, rapid consecutive recordings, interruption, no speech, sleep/wake, and device switching.
  • Offline / rejected provider requests, cleanup failure, app exit before paste, and unsupported paste targets.
  • Multiple displays, full-screen apps, light/dark appearance, Increase Contrast, Reduce Transparency, and Reduce Motion changed while running.
  • VoiceOver labels and announcements, keyboard traversal of rows and editors, enlarged text, and long transcripts.
  • Retention reduction / off, failed writes, correction ambiguity / overlap, stale target scope, and exports with synthetic sensitive text.
